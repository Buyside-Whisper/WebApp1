## Project Overview

A new internal app, built from scratch: Angular 20 (frontend) + NestJS (backend) + PostgreSQL.

Visually, the app copies the CSS/look of `/home/david/Desktop/Job/RetailApp/retailapp-frontend`
(`src/App.css`) — indigo `#4f46e5` accent, white 292px collapsible sidebar, Noto Sans Georgian
font, rounded-pill buttons, 12-24px border radii. **Only the visual styling was copied — no
RetailApp functionality, business logic, or code was reused.** RetailApp is a separate, unrelated
project (a full POS/WMS/restaurant management system) — do not pull in its features or assume
this app should grow in that direction.

Direction: a multi-company ("tenant") product, CRM/ERP-style. A **superuser** (the person who sells
the app) "sells" modules to **companies**; each company's **system admin** runs HR plus the modules
it bought. See "Accounts, roles and access" below, which every module and endpoint must follow.

Current scope: a sidebar with expandable modules, each with submodules. More modules and
submodules are planned, so keep to the structure below.
- **HR** → **Employees** (list with search [name / personal ID / phone / email] and a role filter
  [incl. "No role"], "Add employee" modal, remove; a new person appears in the table at once). Fields:
  first name, last name, personal ID [11 digits, unique per company], email, phone, branch, date of
  birth, hire date, optional end date, **position** [free text: developer, worker, ...; its own table
  column, independent of the role], and an optional **role** [`admin` = module admin / `manager` /
  `cashier`] with a module [`wms`/`store`/`restaurant`, required with a role; cashiers are Store
  only]. Roles are only about permissions and views: **a person with no role has no access to the
  app** (no login, no module unless a module admin/manager added them). Anyone with a role gets a
  login automatically when added (credentials shown once); "Create login"/"Reset password" on a row
  covers people who lost the password. The module under the role badge is shown only to the system
  admin (everyone else only sees their own module, so it would repeat). **Status**
  (`active`/`former`, Georgian გათავისუფლებული = Former) is NOT stored: it's computed from the end
  date (former once the end date is today or past) in the entity's `@AfterLoad` hook and mirrored
  live in the form. All fields except end date are required for new employees (the backend enforces
  it); the DB columns are nullable only because the first employees predate those fields.
  Search/filter happen in the browser (fine at this size; move server-side if the list gets big).
  SMS brand was deliberately left out.
  **TEMPORARY quick-add mode**: the Add employee form currently disables everything except first
  name, position, role (+ module / stores) and fills the rest with random valid data when it opens,
  so test people can be added fast. It is the `QUICK_ADD` constant at the top of
  `features/hr/employees/employees-list/employees-list.ts`; set it to `false` for the full form
  (and delete the quick-add code once the user says so).
- **WMS** → **Warehouses** (CRUD by the **WMS admin only**; the system admin sees all warehouses
  read-only: name, code, branches, type [`main`/`sales`], address, stock,
  status [`active`/`inactive`]). Codes are generated by the backend from the type and numbered:
  `WH-MAIN-01`, `WH-SALE-01`, `WH-SALE-02`, … Changing a warehouse's type gives it a new code.
  Branches are a plain list of names for now; stock is a hand-entered unit count. Each warehouse has
  one **manager** (dropdown of active HR employees with role manager + module WMS); one manager can run
  several warehouses, and a manager sees only his own warehouses, read-only. Which people work in a warehouse is stored
  (`warehouse_employees`, set when a WMS manager adds someone in HR) but not shown on this page.
- **WMS** → **Products** (CRUD by the **WMS admin only**; the system admin sees them read-only;
  managers don't see this page: name, SKU [unique, stored uppercase], category, supplier,
  amount, unit [`kg`/`pcs`], warehouses [many-to-many link to Warehouses]). Amount is the product's
  total quantity: up to 3 decimals for kg, whole numbers for pcs. Category and supplier are plain
  text for now. Warehouse stock is NOT yet computed from products.
- **Store** → **Stores**, **Cash register**, **POS**, **Recording an expense**.
  - *Stores* (CRUD by the **Store admin only**; the system admin sees all stores read-only): name,
    address, **number of cash registers** (default 1, max 50; only
    the Store admin changes it, everyone else sees it read-only) and one manager (picked from HR; a manager can run
    several stores). Managers see their stores read-only. Who works in a store (`store_employees`:
    cashiers, who may open a register there, and role-less people) is set only when a Store manager
    adds someone in HR; it is not shown or editable on this page.
  - *Cash register*: a store has Register 1..N. Before opening, the cashier picks the store and the
    register (registers someone else has open are disabled and show who has them); the database allows
    only one open session per register (partial unique index). The count can't be lowered below a
    register that is open. Each opening is one row (store, register no., cashier, opened/closed,
    transactions, total); click a row to see its transactions. Managers and cashiers open/close their
    own register (one open at a time). Admins see every row, a manager the rows of his stores, a
    cashier only his own. A manager can also work a register ("everything a cashier can do").
  - *POS*: tap catalog products to ring up a sale on your open register. The catalog (`store_products`,
    10 sample items) is the Store module's own, not the WMS products; prices come from the server.
    A company gets the sample catalog when it is sold the Store module.
  - *Recording an expense*: still an empty shell (frontend only).
- **Restaurant** → **Table service**, **Menu management**, **Kitchen screen**, **Waiter view**
  (`/restaurant/table-service`, `/restaurant/menu-management`, `/restaurant/kitchen-screen`,
  `/restaurant/waiter-view`). Empty shells for now: frontend only, "Coming soon". Only admins can reach
  it (no other roles exist for it yet).

The UI is in English. The user sometimes gives requirements in Georgian (e.g. საწყობი = Warehouse,
გასაყიდი საწყობი = Sales warehouse, ერთეული = Unit, ცალი = pcs, პირადი ნომერი = Personal ID
number, გაფორმების თარიღი = Hire date,

## Accounts, roles and access

Read this before adding any module, endpoint or page.

- **Companies** (`companies` table) own all data. `modules` lists what the superuser sold
  (`wms`/`store`/`restaurant`; **HR is always included**).
- **Roles** (`auth/user-role.enum.ts`): `superuser` (no company; own area), `system_admin` (whole
  company: HR + every bought module), `module_admin` (one module + HR limited to that module's people),
  `manager` and `cashier` (one module only, never HR). A system admin is not an employee; the others are
  an `Employee` + a `User` (login) linked by `users.employee_id`. Employees without a login are normal
  (people without a role).
- **Who adds whom**: the superuser creates a company (and its system admin's login) in the superuser
  area. Everyone who has HR can add people **without a role** (no app access). Each level adds exactly
  one role down: the **system admin gives only the module admin role** (his role-less people belong to
  no module; he still sees and can remove/reset anyone in the company). A **module admin gives only
  the manager role** (their own module is forced; if a manager is away they add another manager); his role-less
  people are in his module but in no store. A **Store manager gives only the cashier role**; a **WMS manager
  gives no role** (WMS has no cashiers). Either must tick which of his own stores / warehouses the
  person works in; his HR page shows, and lets him remove / reset the login of, only the people of his
  stores / warehouses. Module admins also *see* their module's cashiers but cannot change them.
  Logins: username + one-time password, stored only as a scrypt hash ("Reset password" gets a new
  one). No emails yet: credentials are shown on screen. Manager-scoped HR knows about the Store and
  Warehouse entities (`store_employees`, `warehouse_employees`), a deliberate exception to module
  independence. There is no edit form
  for employees yet, so a role can't be changed after creation (remove and re-add).
- **Scoping rules, enforced in the backend** (the frontend only hides things):
  - `auth/auth.guard.ts` is a global guard. Controllers declare `@Access('hr' | 'wms' | 'store' |
    'restaurant')` (company must have bought the module and the user must work in it, see
    `auth/access.ts`) and optionally `@Roles(...)` (class or method). `@Public()` skips login.
    `@CurrentUser() user: AuthUser` gives the logged-in user.
  - **Every table that belongs to a company extends `TenantEntity`** (`companies/tenant.entity.ts`,
    adds `company_id`, cascade delete) and **every query must filter by `user.companyId`**. Unique
    constraints are per company (`@Unique(['companyId', 'code'])`). Never accept a company id from the
    client. Services take the `AuthUser` as their first argument.
  - Row-level scoping by role: managers see only warehouses/stores where they are the manager;
    cashiers only their own register sessions (see the services for the pattern). Watch out when
    spreading a scope into `where: { ...scope, id }`: a key present in both (like `id`) is overwritten
    and the scope silently disappears (this was a real bug in manager HR; check membership explicitly).
  - API responses must not leak other people's HR data (managers come back as id + name only).
- **Audit log** (`audit/`): `AuditService.record(user, 'thing.action', 'summary')` for every state-changing
  action. Shown to the superuser (all) and the system admin (own company; HR → Audit log).
- **Auth is a local-development stand-in**: signed tokens are hand-rolled in `auth/token.ts`
  (`AUTH_SECRET` env, 12h), there is no email/invite flow, and the superuser is auto-created on startup
  (`superuser` / `superuser`, override with `SUPERUSER_USERNAME` / `SUPERUSER_PASSWORD` in `.env`).
  Replace with a proper provider (and real invite emails) before anything is shared or deployed.
- **Frontend**: `core/auth/` (session in localStorage, interceptor adds the token and logs out on 401,
  guards, `access.ts` mirrors the backend rules for what to show). `/login` for company users,
  `/superadmin/login` + `/superadmin/*` (own dark layout, `layout/superadmin-shell/`) for the
  superuser; each login page rejects the other kind of account. The sidebar shows only the modules and
  pages the current user may use; route guards (`accessGuard`) protect the URLs.
- **Seed** (`npm run seed`) creates "Demo Company" (all modules) with sample people, warehouses with
  managers, products, stores, and **prints every login once**. To redo it, delete the company in the
  superuser area first. Passwords can't be looked up later, only reset.

## Verifying changes and known gaps

- There is no automated test suite. Access rules were verified with throwaway scripts: create a
  temporary company through the superuser API (`superuser`/`superuser`), build the people you need
  by following the hierarchy, call the API as each role, then delete the company. Never use the
  seeded or real test companies (Apple, Demo Company) for that, and clean up anything you add.
  For UI checks, headless Chrome through the DevTools protocol worked well.
- Not built yet: editing an employee (so a role can't change after creation), voiding / correcting
  a sale (a manager covering a cashier can't undo a wrong scan), real invites / email / auth,
  per-store or per-warehouse editing of members from the admin pages, and the empty shells (Recording
  an expense, all Restaurant pages). Products ignore warehouse members, and warehouse stock is still
  hand-entered.

## Working state and conventions to know

- **Forms:** the Add employee modal and the create-company modal use **reactive forms** with the
  `notBlank` validator and an error-message table; other pages still use template-driven `ngModel`
  with signals (the user is practising the switch). `FormsModule` stays in a component's imports as
  long as any `[(ngModel)]` remains in its template.
- **The user's editor reformats files on save (Prettier)**, so diffs often contain whitespace-only
  line-wrapping changes. Judge changes by behaviour, not by diff size.
- **The user is learning** Angular and NestJS (comes from React) and often asks "how does this
  actually work" questions. Answer with the real mechanism and point at the real files; verify
  against the code or the database instead of describing from memory. They also asked to be told
  when something they want looks like a mistake (see memory notes).

## Structure

Module = folder, submodule = subfolder, and the URL follows the same path on both sides:
sidebar WMS → Products = frontend route `/wms/products` = API `/wms/products`.

**Backend** (`backend/src/`, NestJS + TypeORM + PostgreSQL):
- `<module>/<module>.module.ts` (e.g. `wms/wms.module.ts`) imports its submodules and sets the URL
  prefix with `RouterModule.register([{ path: 'wms', children: [...] }])`. Controllers use only the
  submodule name (`@Controller('products')`). Register new module groups in `app.module.ts`.
- `<module>/<submodule>/` holds `*.entity.ts`, `*.enum.ts`, `dto/`, `*.service.ts`,
  `*.controller.ts`, `*.module.ts` (see `wms/products/` as the most complete example).
- `common/` — helpers shared across modules (numeric column transformer, unique-violation check).
- `auth/` (users, login, guard, decorators), `companies/` (company entity, `TenantEntity`, module enum),
  `audit/` (audit log), `superadmin/` (the superuser's `/superadmin/companies` API). HR employees are
  the shared core: other modules may reference the `Employee` entity (managers, cashiers).
- `store/` has `stores/`, `pos/`, `cash-register/` (POS uses the register sessions that Cash register
  opens: same module, so allowed).
- `seed.ts` — `npm run seed` creates "Demo Company" (skipped if it exists) following the role
  hierarchy; `data-snapshot.ts` — export/import of the whole database (see Running It).

**Frontend** (`frontend/src/app/`, Angular 20, standalone components, zoneless, signals):
- `features/<module>/<module>.routes.ts` — the module's submodule routes (default export), lazy
  loaded from `app.routes.ts` with `loadChildren`. Pages use `loadComponent`.
- `features/<module>/<submodule>/` holds `<name>.model.ts` (types only), `<name>.service.ts`
  (HTTP only, URLs built from `core/api.ts`), and one folder per page (e.g. `products-list/`).
- `layout/` — app frames (`shell/` sidebar for companies, `superadmin-shell/`, not-found page).
  `core/` — app-wide config and `core/auth/`.
- `playground/` (none right now) — put learning/experiment pages here, never in `features/`;
  business modules must not import from it.
- `shared/` — reusable components used across modules. Currently `shared/modal/` (`<app-modal
  [open] title (closed)>`, built on native `<dialog>`; used for "Add employee"). Shared styles
  (tables, chips, `code-tag`, status badges, `form-grid`) live in `src/styles.css`; component CSS
  is only for page-specific bits. Modules may share code via `shared/`/`core/`, not by importing each other
  (a submodule may use another submodule of the same module, e.g. Products uses WarehouseService).
  Also in `shared/`: `credentials-modal/` (one-time login display) and `audit-log/`.
- New pages: `npx ng g c features/<module>/<submodule>/<page> --skip-tests`, then add a route in
  the module's routes file and a link in `layout/shell/shell.html`. All displayed state must be
  signals (the app is zoneless).

## Environment Quirks (learned the hard way — read before reinstalling anything)

- **Node is v22.22.1, npm is v9.2.0** (the system/apt-packaged npm, not a modern nvm-managed one).
- **Angular CLI**: do NOT use `@angular/cli@latest` — version 22.x hard-requires Node `^22.22.3`
  or newer and will refuse to run (not just a warning). Use `@angular/cli@20` instead, which works
  fine with this Node version.
- **`npm install` in `backend/` fails** with `Cannot read properties of null (reading 'edgesOut')`
  — a known bug in npm 9.2.0's Arborist dependency resolver, triggered by Vitest's peer
  dependencies. Fix: always install with `npm install --legacy-peer-deps` in this repo (both
  initial installs and adding new packages).
- **Backend uses NodeNext ESM** (`"type": "module"` + `moduleResolution: "nodenext"`) — every
  relative import needs an explicit `.js` extension even though the source files are `.ts`
  (e.g. `import { Employee } from './employee.entity.js'`).
- **No `sudo` access** in this environment (passwordless sudo isn't configured, and this session
  can't do interactive password prompts) — ask the user to run `sudo` commands.
- **`ng build` (production) needs internet**: it inlines the Google Fonts stylesheet and fails
  with "Inlining of fonts failed" when offline. Use `npx ng build --configuration development` to
  check that the frontend compiles.
- **VS Code Angular template features (hover / Ctrl+Click in `.html`)** need the Angular Language
  Service to attach to `frontend/tsconfig.app.json`. A stray default `tsconfig.json` in
  `/home/David/Desktop/Job/` once swallowed the whole tree (every project under `Job/`) and broke it;
  the user deleted it. If it breaks again, read the extension log under
  `~/.config/Code/logs/<session>/window1/exthost/output_logging_*/*Angular Language Service.log`
  (look for "Enabling language service for ..." and "Could not determine component").
- **`ng` on this machine is NOT Angular**: `ng-common` (a text editor) was once installed by mistake
  and froze terminals via the Angular completion line in `~/.bashrc` (now commented out). Always use
  `npx ng ...` from `frontend/`.

## Running It

```bash
cd backend && npm run start:dev    # NestJS API, port 3000
cd frontend && npm start           # Angular dev server, port 4200
cd backend && npm run seed         # create a "Demo Company" with sample data and print its logins
cd backend && npm run data:export  # write the whole database to backend/data/snapshot.json
cd backend && npm run data:import -- --yes   # DELETE all data in the database, load the snapshot
```

**Moving data between machines** (`backend/src/data-snapshot.ts`, `backend/data/snapshot.json`, committed):
`data:export` on the machine that has the data, commit, pull on the other machine, then
`npm run data:import` (a dry run that only prints what it would delete) and `... -- --yes` to do it.
Rows keep their ids, timestamps and **password hashes**, so the same logins work everywhere. The audit
log is not exported, and the target machine keeps its own superuser. Import wipes everything in the
database named in that machine's `backend/.env`. After a schema change, export again; an old snapshot
may not fit the new tables (the import says so). Tables are discovered from the database, so new
entities are included automatically.

CORS on the backend is currently hardcoded to allow `http://localhost:4200` only
(`backend/src/main.ts`).
